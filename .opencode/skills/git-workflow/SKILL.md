# Git Workflow

## 目的
在 Agentic 開發流程中安全地管理 Git 工作，保護既有修改、維持任務範圍，並留下清楚、可追蹤且適合長期維護的交付歷史。

本 Skill 定義操作原則與必要約束，不規定固定的 Git 指令序列。應依任務情境、Repository 狀態及專案政策，自行選擇合適的 Git 操作方式。

## 核心原則
- Feature Branch 保存開發過程；Main 保存值得長期追蹤的交付歷史。
- Git 操作應服務於工作安全、協作與歷史可理解性，而非追求特定的 Commit 數量或形式。
- 優先遵循 Repository 已存在的規範、團隊協議及使用者明確指示。
- 不確定變更來源、分支所有權或操作影響時，採取保守策略；不要自行推定授權。

## 必要約束

### 1. 保護工作目錄
- 在進行可能影響既有修改的操作前，確認目前分支、工作目錄狀態及變更範圍。
- 區分目前任務產生的修改、既有未提交修改，以及其他 Agent 或使用者留下的工作。
- 不得未經授權覆蓋、丟棄、重設或移動他人的修改。
- 對來源不明或用途不明的變更，先保留並釐清，不要為了讓工作目錄乾淨而自行清除。

### 2. 尊重分支所有權
- 進行歷史改寫、重設或整合前，先確認分支是否由自己建立並獨占管理，或已被其他工作依賴。
- 不得僅憑分支名稱、Commit Author 或目前 Agent 身分推定分支所有權。
- 未經明確授權，不得改寫 Main、Release 或其他共享分支的既有歷史。
- 若分支所有權或依賴關係不明，避免改寫歷史或執行可能影響他人的整合操作，並尋求確認。

### 3. 維持任務範圍
- Commit、Pull Request 與分支整合應聚焦於目前任務及其必要依賴。
- 不要順手混入無關重構、格式化、資產替換或其他清理工作。
- 發現任務範圍外的修改時，先辨識其來源與必要性；若確實需要處理，應明確說明或另行拆分。

### 4. 謹慎處理高風險操作
判斷標準：操作是否難以復原、是否可能丟失工作、是否影響他人或超出目前任務授權。符合任一項即視為高風險，包括但不限於：
- 可能丟失工作目錄內容的操作，例如 `reset --hard`、`clean`、`checkout -- .`、`restore`。
- 丟棄暫存工作，例如 `stash drop`。
- 強制刪除分支，例如 `branch -D`。
- 改寫已分享或可能被他人依賴的歷史。
- Force push 或其他可能覆蓋遠端狀態的操作。

執行前應確認前置條件、影響範圍及操作授權。若可能造成不可逆的工作損失、影響他人，或超出目前任務授權，應先取得人類確認。

高風險不等於一律禁止。例如，若 Feature Branch 明確由目前 Agent 建立並獨占管理，且任務授權包含整理該分支歷史，則可在確認工作安全後自行使用 Interactive Rebase 或其他適當方式。

### 5. 遠端操作需要授權
- 在任務範圍內，Agent 可自行判斷並執行必要的本地 Git 操作，例如建立 Commit 或整理自己管理的分支。
- Push、建立或更新 Pull Request、Merge，以及其他會改變遠端 Repository 狀態的操作，必須有使用者明確要求或既有流程授權。
- 不得因為本地操作已完成，就假設自己也獲得遠端整合或發布授權。

### 6. 不得未授權繞過品質檢查
- 不得未經授權使用 `--no-verify` 或其他方式繞過 Git hooks、簽章政策、CI 或 Repository 品質閘門。
- 若檢查失敗，應理解失敗原因並修正；若無法修正，清楚回報阻礙與影響。
- 不得為了讓 Commit、Push 或 Merge 成功而隱藏檢查失敗。

### 7. 保護敏感資訊
- 提交前檢查 staged changes，避免將 `.env`、API Key、Token、憑證、私鑰或其他敏感資料納入版本控制。
- 若發現敏感資訊已進入 Commit 或遠端歷史，應立即回報。
- Revert 不會移除 Git 歷史中的敏感資料。是否改寫歷史、撤銷憑證或輪替金鑰，應依事件影響及權限交由適當負責人決策；必要時應優先撤銷或輪替已暴露的憑證。

### 8. 留意大型與二進位檔案
- 對貼圖、模型、音訊、影片及其他大型二進位資產，確認 Repository 的資產管理政策、檔案大小限制與 Git LFS 使用方式。
- 不應一概禁止二進位檔案進入 Git；遊戲專案中的 `.png`、`.fbx`、`.blend`、`.wav`、`.asset` 等檔案可能本來就是必要的版本控制內容。
- 若不確定檔案是否應提交、是否需使用 LFS，先確認專案政策再處理。

### 9. 謹慎解決衝突
- 解決 Merge 或 Rebase 衝突前，理解衝突雙方修改的目的與上下文。
- 不得在不了解語意的情況下，單純選擇 ours 或 theirs，或直接刪除其中一方的修改。
- 若無法判斷正確結果，應保留衝突狀態並詢問適當負責人。
- 衝突解決後，執行與變更範圍相稱的檢查，確認整合結果沒有明顯遺漏或破壞。

### 10. 如實回報
- 清楚區分已執行、已驗證及尚未驗證的事項。
- 不得宣稱 Push、PR、Merge、測試或其他操作成功，除非已取得足以確認成功的結果。
- 若任務中止、部分完成、遇到衝突或留下風險，應明確指出目前狀態、尚未完成事項及需要的人類決策。

## Commit 品質
Commit 應以邏輯修改單位切分，而不是依檔案數、行數或固定 Commit 數量決定。

一個有價值的 Commit 通常具備：
- **目的清楚**：能理解這次修改要完成什麼，以及必要時為什麼要做。
- **邏輯完整**：相關修改集中在一起，不把彼此無關的工作混在一起。
- **可追蹤**：日後能透過歷史理解修改內容與脈絡。
- **可回溯**：需要時能合理地檢視、比較或撤銷該修改。

不要求每個 Commit 都能獨立建置或代表可發布狀態；例如，新增必要介面或架構基礎本身就可能是有意義的 Commit。但應避免留下明顯不完整、目的不明或難以理解的中間狀態。

開發過程中可以保留 WIP、修正或 Verifier feedback 等暫時性 Commit。準備提交 Pull Request 或合併前，重新評估哪些歷史值得保留、哪些應合併整理。不要為了追求整齊而過度 Squash，也不要把大量瑣碎修正原封不動留在長期交付歷史中。

## 歷史整理與整合策略
選擇策略時，先判斷希望在目標分支保留哪些歷史資訊，而不是固定使用單一策略。

- **Squash**：適合將一般 Feature Branch 的開發過程整理成一個清楚的交付單位。
- **Rebase**：適合整理自己管理的分支，或保留已具備邏輯獨立性的多個 Commit；不得在未授權下改寫共享歷史。
- **Merge Commit**：適合需要保留分支整合關係、長期整合分支或重要協作拓撲的情境。

專案沒有既定 Merge Strategy 時的預設：
- 一般 Feature PR：優先 Squash Merge。
- 已整理且具技術獨立性的多個 Commit：可使用 Rebase Merge。
- 需要保留整合拓撲或長期分支關係：使用 Merge Commit。

這些是預設判斷，不是不可變更的規則；應依歷史價值、協作方式及 Repository 狀態調整。

## 專案政策優先
操作前先確認 Repository 是否已有既定規範，例如 Branch 命名、Commit message 格式、PR 範本與必要檢查、測試與 CI 閘門、Merge Strategy、受保護分支政策，以及 Git LFS 與資產管理規則。

若已有規範，一律優先遵循，不要以本 Skill 的預設值覆蓋。

若沒有既定規範，才採用以下預設：
- **Branch**：`<type>/<module>-<brief>`，例如 `feat/mining-drop`。
- **Commit message**：標題簡潔描述實際完成的修改；必要時在內文補充原因、設計取捨或重要脈絡；避免 `update`、`fix stuff`、`changes` 等沒有資訊量的訊息。可沿用 Conventional Commits 風格，但不強制。
- **Merge Strategy**：見上節「歷史整理與整合策略」。

## 完成回報
回報內容應與操作規模相稱。簡單操作用一至兩句說明結果即可。

較大型任務至少交代：
- **分支與工作目錄**：在哪個分支完成，是否留下未提交修改。
- **變更內容**：完成了哪些主要修改。
- **Commit 與整合**：建立或整理了哪些 Commit；是否執行 Push、PR 或 Merge。
- **驗證結果**：執行了哪些檢查，以及哪些尚未執行。
- **風險與待決事項**：是否有衝突、未完成工作或需要人類決策的事項。

只回報實際發生的操作與已確認的結果，不要把預計執行的步驟描述成已完成。
